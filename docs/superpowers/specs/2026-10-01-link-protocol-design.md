# بروتوكول ربط العائلات — مواصفة التصميم

> **الحالة:** مسوّدة للمراجعة · **التاريخ:** 2026-10-01 · **المشروع:** ٢ من مسار «ربط العائلات»
> **يعتمد على:** المشروع ١ (تعدد العائلات) — منشور. **يمهّد لـ:** المشروع ٣ (العبور والعرض).

## ١. الهدف

وصل **شخص مشترك** بين شجرتين يملكهما شخصان مختلفان، **بموافقة المالكَين** — عبر «رابط طلب»
(كالدعوة). ينتج رابط `same_person` متبادل بمنح `view_tree`. **لا عبور/عرض فعلي هنا** (المشروع ٣)؛
هذا المشروع يُنشئ **الرابط والموافقة** فقط.

**المثال الحاكم:** زوجتي في شجرتي (عقدة «زوجة»)، ونفسها في شجرة والدها (عقدة «ابنة»). سجلّان
منفصلان في شجرتين مملوكتين لشخصين. التطبيق لا يعرف أنّهما نفس المرأة (لا سجلّ عالمي — خصوصية)،
فلا بد من تأكيد إنسان وموافقة المالكَين، ولأنّ الربط يكشف كلّ شجرة للأخرى.

## ٢. الجمهور والسياق

PWA + ويب، مستودع **عام**، Firebase **Spark المجاني**. يبقى كل شيء على Firestore (لا منتجات مدفوعة).

## ٣. الثوابت المحترمة

- **مصدر الصلاحية `trees/{treeId}/members/{uid}` فقط** — الربط يُنشأ بموافقة المالكَين؛ لا يمنح owner.
- **`personId` ثابت أبدي** — الرابط يشير إلى معرّفات؛ تغييرها يكسرها.
- **لا سجلّ عالمي للأشخاص** — كل شجرة تحتفظ بنسختها؛ الرابط إشارة لا دمج.
- **حذف الشجرة ممنوع** · **`t()` للنص فقط** · المستودع عام (لا أسرار؛ الرمز سرّ يُشارَك خارجياً كالدعوة).
- **كل شجرة سيادية** — الإلغاء من أي طرف يحذف نسخته دون إذن الآخر.

## ٤. نموذج البيانات (على الشكل المحجوز — قرار #٥)

- **`trees/{A}/linkRequests/{token}`** = `{ localPersonId, requestedBy, kind:'same_person', createdAt }`
  — طلب معلّق يولّده مالك A. `token` معرّف تلقائي (كالدعوة).
- **`trees/{treeId}/links/{linkId}`** = `{ localPersonId, remoteTreeId, remotePersonId, kind:'same_person',
  status:'accepted', requestedBy, approvedBy, grantedScope:'view_tree' }` — **نسخة مرآة في كل شجرة**
  (نسخة A تشير لـ B، ونسخة B تشير لـ A). `linkId` معرّف تلقائي مشترك يولّده المُوافِق.

## ٥. التدفّق (رابط طلب)

1. **مالك A** يفتح بطاقة الشخص X → «🔗 ربط بعائلة أخرى» → يُنشئ `linkRequests/{token}` ويحصل على
   رابط `#link=A.token` لنسخه/إرساله.
2. يُرسله لمالك B خارجياً (واتساب…).
3. **مالك B** (مُسجَّل الدخول) يفتح الرابط → يُقرأ الطلب بالرمز → يعرض «عائلة ‹A› تطلب ربط ‹X›» →
   يختار الشخص المقابل **Y** في شجرته (بحث) → **«موافقة»**.
4. الموافقة (`approveLink`) تُنشئ `linkId` واحداً وتكتب **نسختَي الرابط**:
   - `trees/B/links/{linkId}` (يكتبه مالك B — يملك B) → B ترى A: `{localPersonId:Y, remoteTreeId:A, remotePersonId:X, …}`.
   - `trees/A/links/{linkId}` (يكتبه مالك B مُصرَّحاً بوجود الطلب المعلّق في A) → A ترى B:
     `{localPersonId:X, remoteTreeId:B, remotePersonId:Y, viaRequest:token, …}`.
5. يبقى الطلب حتى يُزيله مالك A (أو يُتجاهَل)؛ قائمة طلبات/روابط الشخص تتيح لمالك A الإلغاء.

## ٦. الأمان (قاعدة المؤسسة ٢)

كتلتان جديدتان في `firestore.rules` تحت `/trees/{treeId}` + دالة `linkRequestDoc(treeId, token)`:

```
match /linkRequests/{token} {
  allow get:    if signedIn();                 // المُوافِق يقرأ الطلب بالرمز (كالدعوة)
  allow list:   if isOwner(treeId);            // المالك فقط يسرد طلباته
  allow create: if isOwner(treeId) && request.resource.data.kind == 'same_person';
  allow delete: if isOwner(treeId);            // المالك يلغي طلبه المعلّق
  allow update: if false;
}

match /links/{linkId} {
  allow read:   if isMember(treeId);
  allow create: if signedIn()
                && request.resource.data.kind == 'same_person'
                && request.resource.data.status == 'accepted'
                && request.resource.data.grantedScope == 'view_tree'
                && (
                  // (أ) مالك هذه الشجرة ينشئ نسخته
                  isOwner(treeId)
                  ||
                  // (ب) مُوافِق خارجي ينشئ نسخة هذه الشجرة مُصرَّحاً بطلب معلّق مطابق فيها
                  ( exists(linkRequestDoc(treeId, request.resource.data.viaRequest))
                    && get(linkRequestDoc(treeId, request.resource.data.viaRequest)).data.localPersonId
                         == request.resource.data.localPersonId )
                );
  allow delete: if isOwner(treeId);            // أي مالك يلغي نسخته
  allow update: if false;                      // غير قابل للتعديل؛ الإلغاء = حذف
}
```

- **العزل محفوظ:** لا أحد يكتب في شجرة إلا مالكها، أو عبر **طلب معلّق صريح** فيها (موافقة A).
- `grantedScope` و`kind` و`status` مُقيَّدة في القاعدة فلا تُزوَّر.
- **خطر الرمز المسرَّب** = خطر الدعوة المسرَّبة: يمنح **عرضاً** فقط، متماثلاً، وقابلاً للإلغاء من أي مالك.
- **لا يمنح الرابط أي كتابة** على الشجرة الأخرى — العرض فقط (يُستهلَك في المشروع ٣).
- يُراجَع بوكيلين مختلفين قبل الإعلان؛ تُصلَح نتائج ≥٨٥٪.

## ٧. الواجهة

- **بطاقة الشخص (للمالك):** زر «🔗 ربط بعائلة أخرى» → يولّد الطلب ويعرض `#link=` لنسخه.
  ووسم «🔗 مرتبط بعائلة ‹الاسم›» إن وُجد رابط، مع «إلغاء الربط».
- **فتح `#link=` (مالك B مُسجَّل):** ورقة «طلب ربط من عائلة ‹A›: ‹X›» → حقل بحث لاختيار الشخص Y
  في شجرة B → «موافقة» / «رفض». (غير مُسجَّل → يُطلب الدخول أولاً.)
- التنقّل الفعلي عبر الرابط = **المشروع ٣** (هنا فقط الإنشاء/العرض كوسم).

## ٨. الإلغاء

أي مالك يحذف **نسخته** من `links/{linkId}` (قاعدة delete: isOwner). النسخة المقابلة تصبح «معلّقة»
(تشير لرابط محذوف) ويتعامل معها المشروع ٣ بلطف (وسم «الربط أُلغي من الطرف الآخر»). لا حاجة لإذن الطرف
الآخر — سيادة.

## ٩. الاختبار

1. **منطق نقيّ** (node): تحليل `#link=treeId.token` (مطابق لتحليل الدعوة: strip، decode، split أول نقطة،
   رفض `/`), وبناء حقول نسختَي الرابط من (localX, treeA, Y, treeB).
2. **قواعد** في المحاكي: مالك ينشئ طلباً؛ غير مالك لا؛ قراءة الطلب بالرمز؛ إنشاء نسخة الرابط بمالك
   الشجرة؛ إنشاء نسخة شجرة A بطلب معلّق مطابق (يَنجح) وبطلب مفقود/غير مطابق (يَفشل)؛ القراءة لعضو؛
   الحذف بالمالك فقط؛ منع التعديل؛ العزل عبر المستأجرين.
3. **الواجهة** في المعزل (توليد الرابط، ورقة الموافقة، اختيار الشخص) بمحاكاة `__ftCloud`.

## ١٠. خارج النطاق (المشروع ٣)

- **العبور الفعلي** إلى الشجرة المرتبطة وعرضها (باستخدام `grantedScope: view_tree`).
- **نموذج المشاركة** (لحظات/سجل مشترك).
- أنواع روابط غير `same_person` (زواج/نسب موسّع) — لاحقاً.

## ١١. المخاطر والتخفيف

| الخطر | التخفيف |
|---|---|
| رمز الطلب مسرَّب → ربط خبيث | يمنح عرضاً فقط (لا كتابة)، متماثلاً، وقابلاً للإلغاء — كخطر الدعوة؛ ومالك A يرى/يلغي طلباته ورابطه |
| اختيار الشخص الخطأ Y | المُوافِق يرى اسم X ويبحث عن Y بوعي؛ ويمكن الإلغاء وإعادة الربط |
| طلب معلّق يُعاد استخدامه (نسخ A مكرّرة) | مالك A يرى طلباته المعلّقة ويحذفها؛ وأي رابط زائد يُلغى — أثر محدود (عرض فقط) |
| نسخة رابط معلّقة بعد إلغاء الطرف الآخر | المشروع ٣ يعرض «أُلغي من الطرف الآخر» بلطف |
| قاعدة أمان خاطئة | اختبار محاكي شامل + مراجعة وكيل مختلف قبل النشر |

## ١٢. ترتيب البناء (عناوين — التفاصيل في الخطة)

1. منطق نقيّ: تحليل `#link=` + بناء حقول نسختَي الرابط + اختبار node.
2. قواعد `linkRequests` + `links` + دالة `linkRequestDoc` + اختبار محاكي + مراجعة أمنية.
3. `requestLink(personId)` (توليد الطلب + رابط `#link=`) في cloud.js.
4. `approveLink(...)` (كتابة نسختَي الرابط + تحميل روابط الشجرة) في cloud.js.
5. تحميل روابط الشجرة الحالية (`currentLinks`) وعرض وسم «مرتبط» على البطاقة/البروفايل.
6. واجهة: زر «ربط بعائلة أخرى» (توليد)، معالج فتح `#link=` (ورقة الموافقة + بحث واختيار Y).
7. الإلغاء (حذف نسخة الشجرة) + عرضه.
8. تحقّق في المعزل + نشر القواعد (بموافقة) + دمج ودفع.
