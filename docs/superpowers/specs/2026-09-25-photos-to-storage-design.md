# نقل الصور إلى Firebase Storage — مواصفة التصميم

> **الحالة:** مسوّدة للمراجعة · **التاريخ:** 2026-09-25 · **المشروع:** ٠ من مسار «ربط العائلات»
> **يعتمد عليه لاحقاً:** فيدرالية الأشجار (صورة مشتركة بين شجرتين بإشارة واحدة، بلا تكرار).

## ١. الهدف

إخراج صور الأفراد واللحظات من **مستند الشجرة الواحد** في Firestore إلى **Firebase Storage**،
بحيث يحمل السجل مساراً قصيراً بدل base64. هذا:

1. يزيل سقفاً **حيّاً الآن**: المستند محدود بـ 1MB (حارس عند 900KB)، وصورة الفرد
   (~16–27KB base64) تجعل **٣٥–٥٠ صورة تملأ المستند** فيُرفض الحفظ. عند 146 فرداً هذا سقف فعلي.
2. يخفّض حجم مستند الشجرة نحو **100×**، ويقلّل ذاكرة العميل (لا base64 ضخم في كل لقطة).
3. يمهّد للفيدرالية: الشجرتان المرتبطتان **تشيران لنفس الملف** — لا تكرار للصورة.

## ٢. الجمهور والسياق

عائلات عربية في المهجر، تطبيق PWA + ويب من مصدر واحد، مستودع **عام** (لا أسرار في الكود؛
الحماية في القواعد). مشروع Firebase: `family-tree-app-d9238`، والـ `storageBucket`
مُعرّف أصلاً في `cloud.js`: `family-tree-app-d9238.firebasestorage.app`.

## ٣. الثوابت المحترمة

- **`personId` ثابت أبدي** — مسار الصورة مشتقّ منه (`people/{personId}.jpg`) ولا يغيّره.
- **مصدر الصلاحية `trees/{treeId}/members/{uid}` فقط** — قواعد Storage تقرأ هذا عبر
  `firestore.get`، لا `users/{uid}`.
- **حذف الشجرة ممنوع على الخادم** — لا يتغيّر؛ حذف ملفات Storage عند حذف فرد فقط.
- **`t()` هو الطريق الوحيد للنص** — كل نص جديد عبر جسر الترجمة.
- المستودع عام — لا شيء سرّي يُضاف؛ مفتاح الويب عام بطبيعته والحماية في قواعد Storage.

## ٤. البنية

### ٤.١ وحدة جديدة `photos.js` (وحدة ES، تُحمَّل من `cloud.js`)

مسؤولية واحدة: التعامل مع الصور مقابل Storage. تصدّر:

```
uploadPersonPhoto(treeId, personId, blob) -> Promise<string path>
uploadMomentPhoto(treeId, momentId, blob) -> Promise<string path>
resolvePhotoURL(path) -> Promise<string url>   // getDownloadURL + كاش ذاكرة
deletePhoto(path) -> Promise<void>
```

يستورد `getStorage, ref, uploadBytes, getDownloadURL, deleteObject` من
`firebase-storage.js` (نفس إصدار 10.13.2 المستخدم في `cloud.js`). يبقى الملف صغيراً
ومركّزاً (قاعدة: وحدة لكل شأن).

### ٤.٢ نموذج البيانات

- **الفرد:** حقل جديد `photoPath` (سلسلة مسار Storage، ~60 بايت). يُلغى تخزين base64 في
  `photo` بعد الترحيل.
- **اللحظة:** حقل `photoPath` مثله (يحلّ محل `photo` base64 في اللحظات الجديدة).
- **قاعدة العرض (توافق رجعي):** الحلّ يتم عند العرض بهذا الترتيب:
  1. إن وُجد `photoPath` → `resolvePhotoURL(path)` (رابط مُخزّن مؤقتاً).
  2. وإلا إن وُجد `photo` قديم (base64) → يُستخدم مباشرة.
  3. وإلا → الأيقونة الافتراضية (👨/👩).
  فالقديم والجديد يتعايشان أثناء الترحيل التدريجي دون كسر.

### ٤.٣ تخطيط Storage

```
trees/{treeId}/people/{personId}.jpg     // صورة واحدة لكل فرد؛ الاستبدال يكتب فوقها
trees/{treeId}/moments/{momentId}.jpg    // صورة لحظة
```

المسار مشتقّ من معرّفات ثابتة → إعادة الرفع تستبدل نظيفاً بلا ملفات يتيمة.

### ٤.٤ الرفع

`resizeImage` (في `app.js`) يُعدّل لينتج **Blob** عبر `canvas.toBlob(cb, 'image/jpeg', 0.72)`
بدل `toDataURL`. أحجام التصغير الحالية تبقى (220px للأفراد، 640px للّحظات). ثم
`uploadPersonPhoto/uploadMomentPhoto` يرفع الـ Blob ويعيد المسار الذي يُخزّن في السجل.

## ٥. الأمان — قواعد Storage (تغيير أمني، يُراجَع بوكيل مختلف)

ملف جديد `storage.rules`، ومرجع في `firebase.json` (`"storage": { "rules": "storage.rules" }`).

```
rules_version = '2';
service firebase.storage {
  match /b/{bucket}/o {
    function signedIn(){ return request.auth != null; }
    function memberDoc(treeId){
      return firestore.get(/databases/(default)/documents/trees/$(treeId)/members/$(request.auth.uid));
    }
    function isMember(treeId){
      return signedIn() &&
        firestore.exists(/databases/(default)/documents/trees/$(treeId)/members/$(request.auth.uid));
    }
    function canEdit(treeId){
      return isMember(treeId) && memberDoc(treeId).data.role != 'viewer';
    }
    // صور الأفراد واللحظات: يقرؤها كل عضو، ويكتبها/يحذفها المحرّرون فقط.
    match /trees/{treeId}/{sub}/{fileName} {
      allow read:   if isMember(treeId);
      allow write:  if canEdit(treeId)
                    && request.resource.size < 2 * 1024 * 1024   // سقف 2MB للملف
                    && request.resource.contentType.matches('image/.*');
      allow delete: if canEdit(treeId);
    }
  }
}
```

- العزل متعدد المستأجرين محفوظ: لا وصول إلا لعضو الشجرة صاحبة المسار.
- سقف حجم + نوع صورة يمنع إساءة الاستخدام.
- **القراءة عبر الشجرات (للفيدرالية)** تُضاف لاحقاً في مشروع الربط، لا الآن.

## ٦. الترحيل — تلقائي تدريجي (بلا فقد)

عند تحميل الشجرة، إن كان المستخدم **محرّراً**، تعمل مهمة خلفية هادئة:

1. تمرّ على الأفراد الذين لديهم `photo` (base64) وليس لديهم `photoPath`.
2. لكل واحد: تحوّل base64 → Blob، ترفعه عبر `uploadPersonPhoto`، تضبط `photoPath`،
   ثم **تمسح `photo`** — وترتيب العمليات صارم: **لا يُمسح base64 إلا بعد تأكيد نجاح الرفع**.
3. تحفظ دفعة واحدة بعد عدد محدود (مثلاً 5 في المرة) لتجنّب ضغط الحفظ، وتتوقف عند أي فشل
   شبكة (تُكمل في الجلسة التالية).

**نطاق الترحيل = صور الأفراد فقط** — لأنها من تملأ مستند الشجرة. صور اللحظات القديمة
(base64) تعيش في مستندات منفصلة ولا تهدّد حدّ المستند، فتبقى كما هي (العارض يدعمها)،
واللحظات **الجديدة** فقط تستخدم `photoPath`.

**قبل التفعيل على البيانات الحقيقية: نسخة احتياطية خارج المستودع** (كالمعتاد). الترحيل
تدريجي وآمن ويمكن إيقافه، ولا يلمس شجرة إلا محرّرها.

## ٧. العمل بلا إنترنت — كاش Service Worker

`sw.js`: تُضاف قاعدة **cache-first** لطلبات نطاق Storage
(`firebasestorage.googleapis.com` / `*.firebasestorage.app`): تُخدَم من الكاش إن وُجدت،
وإلا من الشبكة ثم تُخزّن. فالصور المُشاهَدة مرة تعمل بلا إنترنت. رفع صورة جديدة يحتاج شبكة
(مقبول بقرار المالك). كاش الصور منفصل عن كاش الأصول (`family-tree-img-vN`) بحدّ عددي معقول.

## ٨. استراتيجية الاختبار

1. **قواعد Storage** في **محاكي Storage + Firestore** (سكربت مثل `verify-rules.mjs`):
   عضو يقرأ ✓، غير عضو يُمنع ✓، محرّر يكتب ✓، مشاهد لا يكتب ✓، نوع/حجم مرفوض ✓،
   عبر مستأجرين معزول ✓.
2. **منطق حلّ العرض** (path مقابل base64 مقابل الافتراضي) — دالة نقيّة تُختبر في node.
3. **تدفّق الرفع/الترحيل** — يُتحقَّق في **المعزل** (harness بلا `cloud.js` الحقيقي، أو محاكي)،
   **لا يُختبر أبداً على الشجرة الحقيقية**.
4. مراجعة أمنية بوكيل مختلف لقواعد Storage + منطق الترحيل قبل إعلان الانتهاء (قاعدة المؤسسة ٢).

## ٩. التكلفة

Firebase Storage: الباقة المجانية ~5GB تخزين و~1GB/يوم تنزيل — لعائلة، **مجاني عملياً**.
لا يُعطَّل أي منتج أمني لتقليل التكلفة. التكلفة تُبلَّغ إن اقتربت من الحدود.

## ١٠. خارج النطاق (لمشاريع لاحقة)

- تعدد العضويات، بروتوكول الربط، العبور عبر الأشجار، نموذج المشاركة (١/٢/٣).
- القراءة عبر الشجرات في قواعد Storage (تُضاف مع الربط).
- القصص الصوتية (تصبح ممكنة بعد Storage، لكنها مشروع مستقل).

## ١١. المخاطر والتخفيف

| الخطر | التخفيف |
|---|---|
| فقد صورة أثناء الترحيل | لا يُمسح base64 إلا بعد تأكيد الرفع؛ نسخة احتياطية مسبقة |
| قواعد Storage خاطئة تكشف صوراً | اختبار محاكي شامل + مراجعة وكيل مختلف قبل النشر |
| كسر العرض للسجلات القديمة | العارض يدعم القديم والجديد معاً طوال الترحيل |
| الصور لا تظهر بلا إنترنت | كاش SW يخزّن ما شوهد |
| نشر القواعد يدوياً | القواعد تُنشر بأمر Firebase صريح بموافقة المالك، كقواعد Firestore |

## ١٢. ترتيب البناء (عناوين المهام — التفاصيل في خطة التنفيذ)

1. `photos.js` (رفع/حلّ/حذف) + اختبار منطق الحلّ النقيّ.
2. `resizeImage` → Blob.
3. توصيل الرفع في نموذج تعديل الفرد وفي نشر اللحظة (كتابة `photoPath`).
4. العارض يقرأ `photoPath` (مع التوافق الرجعي) في: الكرت، البروفايل، مشاركة الصورة، اكتمال/إحصاءات.
5. `storage.rules` + `firebase.json` + اختبار المحاكي + مراجعة أمنية.
6. الترحيل التلقائي التدريجي.
7. كاش SW للصور.
8. تحقّق في المعزل + نشر القواعد (بموافقة) + نشر الكود.
