# العبور والعرض عبر الشجرات المرتبطة — مواصفة التصميم

> **الحالة:** معتمدة · **التاريخ:** 2026-10-01 · **المشروع:** ٣-أ من مسار «ربط العائلات»
> **يعتمد على:** المشروع ٢ (بروتوكول الربط) — منشور. **يمهّد لـ:** ٣-ب (المشاركة) و٣-ج (إدارة الطلبات).

## ١. الهدف

جعل الرابط **قابلاً للاستخدام**: النقر على وسم «مرتبط بعائلة A» يفتح شجرة A **للقراءة
فقط** متمركزة على الشخص المرتبط. عرض **حيّ** (يعكس تعديلات A)، **كشف متبادل** للشجرة
والملفات دون الدردشة الخاصة، و**عزل تامّ** لحالة الشجرتين. لا كتابة عبر الشجرات أبداً.

**المثال الحاكم:** زوجتي مرتبطة بين شجرتي وشجرة والدها. أنقر وسمها فأعبر إلى شجرة والدها
للقراءة، أرى أهلها وأجدادها، ثم أرجع إلى شجرتي كما تركتها.

## ٢. الجمهور والسياق

PWA + ويب، مستودع **عام**، Firebase **Spark المجاني**. كل شيء على Firestore.

## ٣. الثوابت المحترمة

- **مصدر الصلاحية `trees/{treeId}/members/{uid}` فقط** — مِنحة الزائر **ليست** عضوية
  ولا تمنح أي كتابة؛ القراءة فقط عبر مستند منح منفصل.
- **`personId` ثابت أبدي** · **لا سجلّ عالمي** · **حذف الشجرة ممنوع** · **`t()` للنص فقط**.
- **كل شجرة سيادية** — الزائر يُلغي عرضَه، والمالك يطرد أي زائر؛ أيٌّ منهما دون إذن الآخر.
- **عزل الحالة مقدّس** — عرض شجرة أخرى لا يلمس `state`/localStorage/سحابة المستخدم إطلاقاً.

## ٤. نموذج البيانات (إضافة واحدة)

- **`trees/{t}/viewers/{viewerUid}`** = `{ grantedBy, viaRequest?, remoteTreeId, at }`
  — مِنحة قراءة محدَّدة المسار بمعرّف الزائر (كي تفحصها القاعدة بـ`exists()`؛ القواعد لا
  تستعلم عن مجموعة). `remoteTreeId` = الشجرة التي يملكها الزائر (للعرض/الإلغاء المتبادل).
  **لا تغيير** على `links`/`linkRequests`.

عند الموافقة (`approveLink`) تُضاف كتابتان للمِنحة داخل **نفس الـ`writeBatch` الذرّي**
الموجود:
- `trees/B/viewers/{A}` (يكتبه B — يملك B) → A يرى B.
- `trees/A/viewers/{B}` (يكتبه B مُصرَّحاً بالطلب المعلّق، بقيد `viewerUid == uid()`) → B يرى A.

## ٥. التدفّق

1. **الموافقة:** `approveLink` تكتب — ذرّياً — نسختَي الرابط + مِنحتَي الزائر (أربع كتابات،
   الكل أو لا شيء).
2. **العبور:** في بطاقة الشخص، وسم «🔗 مرتبط بعائلة A» يصبح **قابلاً للنقر** → يستدعي
   `viewLinkedTree(remoteTreeId, remotePersonId)`.
3. **العرض:** تُحمَّل شجرة A بقراءة واحدة (`getDoc`) في **حالة عرض منفصلة**، تُرسَم للقراءة
   فقط متمركزة على الشخص، مع شريط «عرض: عائلة A (قراءة فقط)» وزر رجوع. مزامنة شجرة
   المستخدم **موقوفة** طوال العرض.
4. **الرجوع:** تُستعاد حالة المستخدم كما كانت، وتُستأنف المزامنة.
5. **عند القطع:** لو حاول A فتح شجرة B بعد أن قطع B، تُرفض القراءة → «أُلغي من الطرف الآخر»
   بلطف. فحص الوصول وقت العرض هو مصدر الحقيقة (لا مزامنة حالة).

## ٦. الأمان (قاعدة المؤسسة ٢)

دالة + كتلة + تعديل قراءتين في `firestore.rules`:

```
function viewerDoc(treeId, user) {
  return /databases/$(database)/documents/trees/$(treeId)/viewers/$(user);
}
function canViewTree(treeId) {
  return isMember(treeId) || (signedIn() && exists(viewerDoc(treeId, uid())));
}

match /trees/{treeId} {
  allow read: if canViewTree(treeId);          // كان isMember — يكشف الأشخاص/النسب/التواريخ
  // ... (create/update/delete بلا تغيير)

  match /photos/{photoId} {
    allow read:           if canViewTree(treeId);   // كان isMember — يكشف الصور
    allow create, update: if canEdit(treeId);       // الكتابة بلا تغيير
    allow delete:         if canEdit(treeId);
  }

  // تبقى isMember كما هي (الدردشة الخاصة وقائمة الأعضاء محجوبة عن الزائر):
  //   members, moments, moments/reactions, moments/comments, activity, links, linkRequests

  match /viewers/{viewerUid} {
    allow get:    if isMember(treeId) || viewerUid == uid();
    allow list:   if isOwner(treeId);                      // المالك يرى زوّاره
    allow create: if signedIn() && (
                    isOwner(treeId)
                    || ( viewerUid == uid()
                         && exists(linkRequestDoc(treeId, request.resource.data.viaRequest)) )
                  );
    allow delete: if isOwner(treeId) || viewerUid == uid();  // سيادة الطرفين
    allow update: if false;
  }
}
```

- **الكتابة مغلقة تلقائياً:** الزائر ليس عضواً، فكل `isMember`/`canEdit` للكتابة تبقى مرفوضة.
- **لا كشف للدردشة ولا لقائمة الأعضاء:** قراءات moments/activity/comments/members تبقى isMember.
- **خطر الرمز المسرَّب** = خطر الدعوة: يمنح قراءةً فقط، قابلة للإلغاء من أي طرف.
- يُراجَع بوكيلين مختلفين؛ تُصلَح نتائج ≥٨٥٪.

## ٧. الواجهة

- **بطاقة الشخص:** الوسم الموجود يصبح زرّاً `data-view-link` يحمل `remoteTreeId`+`remotePersonId`.
- **وضع العرض (قراءة فقط):**
  - شريط علوي ثابت «عرض: عائلة ‹A› — قراءة فقط» + زر رجوع.
  - الشجرة تُرسَم من حالة عرض منفصلة؛ كل أدوات التحرير مخفية/معطّلة (`__ftSetEditable(false)`
    + إخفاء أزرار الإضافة/التعديل/الحذف).
  - **عزل الحالة:** حفظ مرجع لحالة المستخدم، إيقاف اشتراك السحابة وأي دفع، تحميل شجرة A
    للعرض، وعند الرجوع استعادة الحالة واستئناف الاشتراك. **لا كتابة في localStorage ولا
    سحابة أثناء العرض.**
  - الصور تُحلّ من `trees/A/photos` (القراءة مسموحة بالمنحة).
- **فشل الوصول:** رسالة «أُلغي من الطرف الآخر» + رجوع.

## ٨. الإلغاء

عند إلغاء الرابط، يحذف B: `trees/B/links/{id}` + `trees/B/viewers/{A}` + `trees/A/viewers/{B}`
(الثلاثة مُصرَّحة: الأولان بالملكية، الثالث بـ`viewerUid==uid()`). نسخة `trees/A/links/{id}`
تبقى معلّقة ويتعامل معها العرض بلطف. المالك يستطيع طرد أي زائر بحذف مستند منحه مباشرة.

## ٩. الاختبار

1. **منطق نقيّ** (node): اختيار شجرة العرض من الرابط + بناء حقول مِنحة الزائر (lib صغيرة).
2. **قواعد** في المحاكي: عضو يقرأ · زائر بمنحة يقرأ الشجرة والصور · زائر بلا منحة يُرفض ·
   الزائر **لا يقرأ** moments/members · إنشاء المنحة بالمالك وبالطلب المعلّق (ينجح) وبلا
   طلب/لغير النفس (يفشل) · الزائر **لا يكتب** شيئاً في الشجرة · الحذف بالزائر لنفسه وبالمالك ·
   العزل عبر المستأجرين.
3. **الواجهة** في المعزل: العبور يحمّل حالة عرض منفصلة؛ **التأكّد أن حالة المستخدم
   وlocalStorage لم تُمسّا**؛ الرجوع يستعيدها؛ فشل الوصول يعرض الرسالة.

## ١٠. خارج النطاق (مشاريع لاحقة)

- **٣-ب المشاركة:** كتابة/عرض لحظات أو سجلّ مشترك عبر الشجرات المرتبطة.
- **٣-ج إدارة الطلبات:** واجهة لمالك A لرؤية/حذف `linkRequests` المعلّقة (الرمز لا يُستهلَك
  حالياً؛ مُخفَّف بإزالة التكرار في العرض).
- كشف اللحظات/السجلّ للزائر · أنواع روابط غير `same_person`.

## ١١. المخاطر والتخفيف

| الخطر | التخفيف |
|---|---|
| عرض شجرة A يلوّث شجرة B الحقيقية | عزل حالة صارم: إيقاف المزامنة، حالة عرض منفصلة، لا كتابة localStorage/سحابة، استعادة عند الرجوع — **أخطر نقطة، تُختبر صراحة** |
| مِنحة الزائر تبقى بعد إلغاء الرابط (تسريب قراءة) | المِنحة قابلة للحذف بـ`viewerUid==uid()`؛ الإلغاء يحذف الثلاثة؛ والمالك يطرد مباشرة |
| رمز الطلب مسرَّب → منح قراءة خبيث | قراءة فقط، متماثل، قابل للإلغاء — كخطر الدعوة |
| الزائر يقرأ دردشة/إيميلات العائلة | قراءات moments/activity/comments/members تبقى isMember (لا canViewTree) |
| قاعدة قراءة متقاطعة خاطئة | اختبار محاكي شامل + مراجعة وكيل مختلف قبل النشر |

## ١٢. ترتيب البناء (عناوين — التفاصيل في الخطة)

1. منطق نقيّ: بناء حقول مِنحة الزائر + اختيار شجرة/شخص العرض من الرابط + اختبار node.
2. قواعد `viewers` + `canViewTree` + تعديل قراءتَي الشجرة والصور + اختبار محاكي + مراجعة أمنية.
3. `approveLink`: إضافة كتابتَي المِنحة للـ`writeBatch`؛ `revokeLink`: حذف المِنحتين.
4. `viewLinkedTree(remoteTreeId, personId)` في cloud.js: قراءة الشجرة + تسليمها للعرض.
5. وضع العرض للقراءة فقط في app.js: عزل الحالة، الشريط، الرجوع، معالجة فشل الوصول.
6. جعل وسم البطاقة قابلاً للنقر + ربطه.
7. تحقّق معزول (خاصة عدم تلوّث حالة المستخدم) + نشر القواعد (بموافقة) + دمج ودفع.
